# 웹 덮개 팝업 판단 설계와 시연 모드 완화안 (B, 10/30)

담당: 준영(B). AGENTS 9장 B 10/30 기한 산출물. 근거는 API 37 에뮬레이터 크롬 덤프(`uiautomator dump`, 2026-10-30)와 main(69432b1), A 통합 브랜치(`fix/a-samsung-p01-lifetime-20261028`) 코드다. **실기기 결과가 아니다.** 덤프 원문은 저장소에 넣지 않았고, 구조만 아래에 적는다.

## 1. 결론

1. 크롬은 웹 팝업이 `role="dialog"`이면 칸 목록에 **`android.app.AlertDialog` 칸**으로 내보낸다. 그래서 B의 기존 같은 화면 덮개 범위(`dialogScope`: 가장 바깥 Dialog 칸이 정확히 하나)가 **웹에서도 그대로 동작한다.** 새로 만들 것은 범위 찾기가 아니라 아래 네 가지다.
2. **막히는 곳은 범위가 아니라 네 군데다.**

   | 막히는 곳 | 담당 | 실제로 본 것 |
   |---|---|---|
   | ① 화면 전체 보호 검사(F0)가 크롬 페이지를 통째로 막음 | A | 주소창이 `EditText`(입력 칸), 바닥글에 "로그인", "고객센터", "개인정보처리방침" |
   | ② 실제 닫기 이름이 허용 목록에 없음 | 공용 계약 + A | 11번가: "앱설치 안내 레이어 닫기", "모바일 웹으로 볼래요" |
   | ③ 보이지 않는 바닥글 글자가 팝업 판단에 섞임 | B | 11번가 바닥글 "[당첨자공지]…" → 사기 의심, "로그인" → 결정 |
   | ④ 앱 설치 유도 문구가 광고로 안 잡힘 | B | "앱에서만 제공되는 혜택을…", "11번가 앱에서 확인" → 판단 불가 |

3. A의 실행 쪽도 같은 화면 덮개를 받지 못한다. 팝업 창 크기가 화면과 같으면 `WINDOW_UNBOUNDED`로 거부하고, 닫기 이름을 6개로 따로 정해 쓴다(5절).

## 2. 크롬에서 실제로 본 구조

- 화면 위 크롬 도구 막대
  - `ImageButton[home_button]`
  - `EditText[url_bar]`: password=false, clickable, 주소가 text로 들어 있음
  - `ImageButton[menu_button]` 등
- `WebView` 안 웹 내용
  - 칸 종류는 대부분 `View`, `Button`, `TextView`, `Image`다.
  - 위쪽 앱 열기 배너 `View[banner]`: "11번가 앱에서 앱 한정 혜택 받기", "앱 열기", `Button` "닫기"
  - **바닥 시트 `AlertDialog` [0,1632][1080,2337]**, 자식 칸은 다음과 같다.
    - `Button` "앱설치 안내 레이어 닫기" (클릭 가능)
    - `View` 안 `TextView` "앱에서만 제공되는 혜택을 놓치고 계신 건 아닌가요?", "지금 바로 11번가 앱에서 확인해보세요!"

    - `Button` "모바일 웹으로 볼래요" (클릭 가능, 사실상 닫기)
  - 바닥글: 높이 0인 칸(`[x,2337][x,2337]`)에 다음 글자가 있다. 화면에 보이지 않는다.
    - "로그인", "고객센터", "이용약관", "개인정보처리방침"
    - "[당첨자공지] 10월15일 … 이벤트"

- 바닥글에 "로그인", "개인정보처리방침", "고객센터"가 있다.

**옥션** (`m.auction.co.kr`)

## 3. B가 바꿀 것 (B 코드, 이번 브랜치)

### 3-1. 보이지 않는 글자는 판단에서 뺀다 (③, 완화가 아니라 수정)
- **기준:** 칸의 넓이가 0이거나 화면 밖에 있는 글자는 사람이 볼 수 없다. TalkBack도 화면 밖 칸은 스크롤 전에는 읽지 않는다.
- **같은 화면 덮개일 때:** `DecisionPopupScope.texts`가 팝업 밖 글자 중 보이지 않는 글자는 **경고 문구라도 뺀다.** 팝업 안 글자는 그대로 둔다.
- **이유:** 페이지 맨 아래 "당첨자공지" 링크 때문에 앱 설치 안내를 사기로 보거나, "로그인" 링크 때문에 결정으로 보면 웹에서는 아무것도 처리할 수 없다.
- **보이는 경고는 그대로 둔다.** 팝업 바로 뒤에 보이는 "결제하기"는 여전히 묻는 근거다(기존 규칙 유지).

### 3-2. 앱 설치·앱 열기 유도는 광고로 본다 (④)
- **광고 문구 추가 (`extraAdKo`):**
  - 앱에서(만) + 혜택·확인·보기·열기
  - 앱 열기, 앱으로 보기, 앱 설치, 앱 다운로드
  - 앱 전용·한정 + 혜택·쿠폰·특가
- **순서는 그대로다.** 사기("긴급 설치"), 결정, 판단 불가 다음에만 본다. "앱 설치하고 혜택 받기"(평가 ad-19, 못 맞힌 7개 중 하나)도 광고가 된다.
- 버튼 "앱 열기", "11번가 앱에서 확인"은 이름 규칙에서 P(이동)·O(모호) 등급이라 **누를 대상은 되지 않는다.**

### 3-3. 시연 후보별 "지금 B 예상"을 정답지 옆에 둔다
D 정답지(`real_site_answer_key.csv`)의 `expected_kind`는 사람 기준이다. 리허설 때 원인을 바로 찾을 수 있게 B 예상을 따로 준다. 6절 표를 참고한다.

## 4. 공용 계약 변경 제안 (②, 팀 합의 필요)

`core/model/ButtonLabelRules`는 A·B·C가 같이 쓰는 계약이라 B 혼자 바꾸지 않는다. 시연 모드(AGENTS 6-0 초안)에 맞춰 v2를 제안한다.

| 제안 | 규칙 | 예 | 막는 것 |
|---|---|---|---|
| **v2-a "○○ 닫기"** | 이름이 "닫기"로 끝나고, 앞부분에 D(결정)·K(조건부) 단어가 없으면 CLOSE. 앞부분은 무엇을 닫는지 설명하는 말이므로 P(이동) 단어("설치", "안내")는 허용 | "앱설치 안내 레이어 닫기", "레이어 닫기", "배너 닫기", "속보 닫기" | "오늘 하루 닫기"(K), "구매창 닫기"(D), "닫기 전 저장"("닫기"로 안 끝남) |
| **v2-b 웹으로 계속 보기** | 앱 설치 유도에서 웹에 남는 말을 CLOSE로 봄: "모바일 웹으로 볼래요/볼게요", "웹으로 계속 보기", "모바일웹으로 보기" | 11번가 바닥 시트 | 앞뒤에 D·K 단어가 붙으면 거부 |

- **v2-a는 안전 쪽으로 근거가 있다.** 마지막 말이 "닫기"이고 결정·조건부 단어가 없으면, 그 버튼이 하는 일은 무언가를 닫는 것이다.
- **v2-b는 시연 모드 완화다.** 끝까지 지키는 것(결제·구매·동의·권한·구독·삭제 비실행, 사기 경고)에는 영향이 없다.
- A의 `F9AutoCloser.role()`은 자체 목록 6개("닫기", "창 닫기", "팝업 닫기", "close", "Close", "dismiss")를 쓴다. 이미 공용 규칙(14개)과 다르다. 지금도 B가 "광고 닫기"를 고르면 A가 `CHOICE_TARGET`으로 거부한다. **A가 `ButtonLabelRules.roleOf`를 그대로 쓰도록 바꾸는 것이 v2보다 먼저다.**

## 7. 끝까지 지키는 것

- 결제·구매·동의·권한·구독·삭제 버튼은 어떤 완화에서도 누르지 않는다. 범위 안의 결정 단어는 그대로 거부한다.
- 사기 문구가 **보이는** 팝업은 경고만 한다.
- 화면 원문은 로그와 저장소에 남기지 않는다. 이 문서의 예시 문구는 공개 페이지 화면이고, 덤프 파일은 넣지 않았다.

## 8. 남은 확인

- 실기기 크롬(재호·우진)에서도 `AlertDialog` 칸이 나오는지 확인해야 한다. 사이트가 `role="dialog"`를 안 쓰면 Dialog 칸이 없어서, 지금 규칙으로는 범위를 못 잡는다. 그런 사이트가 시연 후보에 있으면 별도 규칙(화면 아래 고정 시트 + 닫기 버튼 묶음)을 11/2 "덮개 실행 근거"에서 정한다.
- 크롬 덤프 방법: 도와줄 앱에 크롬을 넣고 접근성 서비스가 켜진 상태에서 `uiautomator dump`를 두 번 실행한다(첫 번째는 웹 내용이 비어 있음).
