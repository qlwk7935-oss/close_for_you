## 1. "구매하기" 버튼이 있는 홍보 팝업 (구매 오판)

### 1-1. 문제

- **지금 동작:**
  - 팝업 버튼 이름에 "구매"가 있으면 B 분류기가 팝업 전체를 **중요한 결정**으로 봅니다(`DecisionKinds` 2단계, 버튼 이름 검사).
  - 시연 엔진은 이걸 `DenyDecision`으로 처리합니다. 선택 창에서는 버튼으로 이동만 하고, 대신 닫지 않습니다.
- **실제로 걸리는 곳:**
  - 중간발표 10쪽 모아마켓 P31: "주말 한정 최대 50% 할인", "지금 구매하기", "오늘 하루 보지 않기", X(닫기)
  - D 정답지에서 이벤트 팝업에 BUY 금지 버튼이 있는 후보 6곳: L04 11번가, L05 G마켓, L06 옥션, L13 인터파크, L15 무신사 앱, L16 CGV 앱
  - 정답지는 이 6곳을 모두 "광고, 닫기 가능"으로 적었는데, 지금 B는 결정으로 봅니다.
- **사용자에게 생기는 문제:**
  - 쇼핑몰 홍보 팝업에는 거의 늘 구매 버튼이 붙어 있습니다.
  - 그래서 "전부 닫기"를 골라도 가장 흔한 광고 팝업을 닫지 못합니다.
  - 시각장애인은 팝업마다 버튼으로 이동해서 직접 닫아야 하고, 이건 앱이 풀려던 문제 그대로입니다.

### 1-2. 목표

- 홍보 팝업의 **닫기 버튼**은 누를 수 있게 합니다.
- **구매 버튼은 여전히 절대 누르지 않습니다.**
- 진짜 결제·주문 화면은 지금처럼 결정으로 남깁니다.

### 1-3. 왜 이게 안전한가 (핵심 논리)

AGENTS 6-1은 "중요한 결정은 **자동 실행하지 않는다**"입니다.
- 홍보 팝업의 닫기를 누르는 것은 구매를 실행하는 게 아니라 **구매 권유를 거절하는 것**이라 되돌릴 손해가 없습니다.
- 위험은 하나뿐입니다. **진짜 결제 확인 창을 홍보로 잘못 보는 것**입니다.
- 그래서 규칙의 조건은 모두 "결제 창의 흔적이 하나라도 있으면 결정으로 남긴다"는 쪽으로 만들었습니다.

### 1-4. 규칙 (`DecisionDemoRules.isPromoPurchase`)

아래 **네 가지가 모두 맞을 때만**, 결정 검사(2단계)에서 **구매 버튼 글자만** 뺍니다. 다른 결정 신호는 전부 그대로 검사합니다.

**① 구매 권유 버튼이 있다**
- **조건:** 이름 **전체**가 다음 형태입니다.
  - (지금|바로|오늘|특가로)? + (구매|주문) + (하기|하러 가기)?
  - 영어: buy now, shop now, order now
- **이유:** 홍보 팝업의 버튼은 짧은 권유 문구입니다. 이름 전체를 보는 이유는 아래처럼 다른 일을 하는 이름을 빼기 위해서입니다.
  - "구매 확정", "구매 동의": 확정·동의
  - "1개 구매": 수량을 고른 실제 주문
  - "로그인하고 구매하기": 로그인
  - "구매하시겠어요?": 질문

**② 홍보 문구가 있다**
- **조건:** 버튼 말고 **다른 글자**에 B의 광고·쿠폰 문구가 있습니다(할인, 특가, % 할인, 쿠폰, 적립금…, 화면 정보 글자만).
- **이유:** 구매 버튼만 있고 홍보 문구가 없는 창("새 상품이 입고되었습니다 / 구매하기")은 홍보라는 근거가 없으니 결정으로 남깁니다.

**③ 팝업 본문이 결정을 권하지 않는다**
- **조건:** 버튼 말고 다른 글자에 결정 단어가 **없습니다.** 혜택 조건으로 쓴 것("지금 구매하면 쿠폰 증정")도 안 됩니다.
- **이유:** 과잉 경고 시험 de-08("광고 / 지금 구매하면 쿠폰 증정 / 구매하기")은 팀이 **결정**으로 정답을 정해 둔 문구입니다.
  - 처음 규칙은 이걸 광고로 바꿔서, 안전 시험이 실패했습니다.
  - 정답을 바꾸는 대신 규칙을 좁혔습니다. 결정을 권하는 말은 **버튼에만** 있어야 합니다.

**④ 결제 창의 흔적이 없다**
- **조건:** 팝업의 어떤 글자에도 아래가 없습니다. 띄어쓰기·전각을 바꿔 써도 찾습니다.
  - 결제, 카드, 계좌, 비밀번호
  - 약관, 동의
  - 자동 갱신·결제, 정기, 구독
  - 수량, 배송지
  - 총 금액·가격, 주문 내역·확인·금액·정보
  - (구매|주문|결제)하시겠, 할까요, 드릴까요
  - checkout, payment, subscribe, terms, agree
- **이유:** 진짜 결제·주문 창에 늘 있는 말입니다. 하나라도 보이면 홍보가 아니라 거래 창일 수 있으니 결정으로 남깁니다.
  - 가격("41,000원")은 홍보 팝업에도 늘 있어서 흔적으로 보지 않습니다. 대신 "총 결제 금액"처럼 결제 문맥이 붙은 금액은 흔적입니다.

**시연 엔진 쪽 (`SimpleCloseDecider`)**
- 위 규칙이 켜져 있고 B가 광고·쿠폰으로 판단했을 때만, **구매 권유 버튼은 "위험 버튼 수"에서 뺍니다**(`ButtonScan.promoBuyCount`).
- 이때도 구매 권유 버튼은 누를 후보가 아닙니다(`candidates`에 들어가지 않음). 강력 모드가 누르는 건 여전히 닫기뿐입니다.
- 다른 위험 버튼(회원가입, 예약 등)이 하나라도 있으면 지금처럼 묻습니다.

### 1-6. 남은 위험과 질문

- **위험:** 결제 창인데 위 흔적이 하나도 없고, 홍보 문구와 "구매하기"만 있는 경우입니다(예: "특가 41,000원 / 구매하기"만 있는 즉시 구매 창).
  - 이 경우에도 앱이 누르는 건 **닫기**뿐이라 구매가 일어나지는 않습니다. 사용자가 그 창이 떴다는 걸 모른 채 닫힐 수 있는 것이 손해입니다.
- **질문 1:** 이 정도면 시연 모드에서 켜도 될까요? 저는 켜는 쪽을 제안합니다.
- **질문 2:** 끄더라도 A·C 쪽 선택 창에서 "구매하기는 누르지 않고 닫기만 누를게요"라고 안내하는 방식은 어떨까요?
- **켜는 법:** `DecisionDemoRules.PROMO_PURCHASE = true` 한 줄입니다.
  - 시연 엔진 연결은 이미 되어 있습니다. `SimpleCloseAccessibilityService`에 인자 하나(`promoBuyCount`)를 넘기는 한 줄을 추가했고, 이 줄만 재호 파일입니다.

### 1-7. "결제 혜택·결제 할인" 홍보 문구 (재호 요청, LG 올리브영)

**문제**
- LG 올리브영 앱의 어두운 배경 위 서랍 안에 "결제 혜택 총정리 블프 특가에 결제 할인까지! … 리워드 받기" 배너 링크가 있습니다.
- B가 이 팝업을 **중요한 결정**으로 분류했습니다(로그 `DETECTED_DIM_OVERLAY → CLASSIFIED_DECISION → DECISION_ASKED`). 그래서 선택 창 첫 줄이 "'…리워드 받기' 버튼으로 이동"이 됐습니다.
- **원인:** "결제"가 B의 결정 단어 목록에 그대로 들어 있어서, 홍보 문구 안의 "결제"도 결정으로 셌습니다.
  - R1 예외는 "결제 **시**", "결제**하면**" 같은 조건 형태만 빼 줬고, "결제 혜택", "결제 할인" 같은 이름 형태는 빼 주지 않았습니다.

**재현:** 단위 시험에 같은 문구를 넣으면 고치기 전에 `USER_DECISION`이 나왔습니다(`DecisionPaymentBenefitTest`).

**규칙 제안**
- **결제 수단 혜택 문구는 R1처럼 혜택 언급으로 봅니다.**
  - 대상: (카드·간편·계좌·현금·앱·○○페이)? + 결제 + (시)? + 혜택·할인·적립·캐시백·이벤트·프로모션·쿠폰·리워드
  - 예: "결제 혜택", "결제 할인", "카드 결제 시 할인", "네이버페이 결제 적립"
- **그 문구만 빼고**, 옆에 있는 다른 결정 신호는 그대로 셉니다.
  - "카드 결제 시 5% 할인" + "결제하기" 버튼 → 결정
  - "결제 혜택 안내" + "결제 수단을 선택하세요" → 결정
  - "결제 할인을 받으시겠어요?" → 질문이라 결정
  - "자동 결제 할인 혜택" → 자동 결제라 결정
  - "결제 혜택을 받으려면 약관에 동의" → 동의라 결정
  - "결제 할인 받고 지금 결제하세요" → 결제 요구라 결정
- **시연 엔진의 위험 버튼 검사(`isRisky`)도 같은 기준입니다.**
  - 긴 배너 링크(10자 초과)만 해당합니다. "결제하기", "결제 할인"처럼 짧은 버튼은 그대로 위험 버튼입니다.
  - 이유: 버튼 이름이 짧으면 그 버튼이 곧 결제 동작이기 때문입니다(R1의 "10자 이하는 버튼 이름" 기준과 같음).
- **구매 오판 규칙(1-4)의 ③·④도 같은 기준을 씁니다.**
  - 결제 **수단** 혜택만 뺍니다.
  - "지금 구매하면 쿠폰 증정"(de-08) 같은 **구매** 조건은 빼지 않습니다. 구매 결정 자체를 권하는 말이라서입니다.
  - 구현 중 "카드 결제 시 10% 할인"의 "카드"가 결제 흔적으로 남는 문제를 시험이 잡아서, 결제 수단 이름까지 함께 빼도록 고쳤습니다.

**왜 안전한가:** 빼는 것은 "어떤 결제 수단을 쓰면 혜택이 있다"는 **홍보 문장**뿐입니다. 결제를 실행하거나 요구하는 말(결제하기, 결제 수단 선택, 자동 결제, 질문, 동의)은 하나도 빼지 않습니다.

**검증**
- 올리브영 배너: 결정 → **광고**, 위험 버튼 아님
- 결제 수단 혜택 4종은 혜택 언급, 실제 결제 단계 6종은 결정 유지, 짧은 버튼 2종은 위험 유지
- B 평가 기준값(새 문구 80개·82개·과잉 경고 35개) **변화 없음**, 실제 덤프 재생 결과도 같음
- debug 단위 시험 1,182개 통과

### 1-8. "○○ 혜택 구매하러가기" 광고 링크 (재호 요청, LG 옥션 11/2, 제안)

**문제.** 옥션 웹의 광고 이미지 설명이 "삼성 BIG 혜택 구매하러가기"인 팝업이 `BUTTONS_RISKY=1` → `CLASSIFIED_DECISION` → 묻기로 갔습니다. 1절 규칙은 버튼 글자 전체가 "구매하러 가기"일 때만 홍보로 봐서, 앞에 혜택 이름이 붙으면 구매 버튼으로 잡힙니다. 쇼핑몰 광고에 흔한 모양이라 시연에서 자동 닫기가 안 될 수 있습니다. 갤럭시에서 옥션이 결정으로 분류된 1번도 같은 경우일 수 있지만, 그때 화면을 못 봐서 확정은 못 했습니다.

**제안 규칙.** 아래를 모두 만족하면 홍보 링크로 봅니다. 나머지 1절 조건(결제 흔적 없음, 다른 글자에 결정 문구 없음)은 그대로입니다.

**닫기 조건(재호 요청).** 이름 있는 닫기가 있을 때만 닫습니다. 라벨 없는 X만 있으면 계속 묻습니다(6-3).

## 2. 브라우저 민감 사이트 기준 (`BrowserSensitivity`)

### 2-1. 문제

- A의 민감 앱 차단(#65, `SensitiveAppRules`)은 **앱 단위**입니다. 크롬은 쇼핑몰도 은행도 같은 앱이라 막을 수 없습니다.
- 시연 엔진은 크롬 화면을 읽고 팝업을 누릅니다. 그런데 `SimpleTreeCollector`에는 **비밀번호 칸이나 민감 페이지 검사가 없습니다.**
  - 원래 A의 F0에 있던 `isPassword`·입력 칸·민감 단어 검사가 시연 엔진에는 없습니다.
- 그래서 지금은 은행 로그인 페이지나 결제 페이지에 뜬 팝업도 읽고 누를 수 있습니다.

### 2-2. 목표

- 로그인, 결제, 은행·카드·증권, 정부 서비스, 개인정보가 보이는 페이지에서는 **아무것도 읽어 판단하거나 누르지 않습니다.** TalkBack은 평소대로 동작합니다.
- 반대로 **쇼핑몰 홈 화면은 막지 않습니다.** 시연 대상이기 때문입니다.

### 2-3. 왜 단어만으로는 안 되나 (실측 근거)

- 11번가 홈 덤프의 바닥글에 "로그인", "고객센터", "개인정보처리방침"이 있고, 크롬 주소창도 입력 칸(`EditText`)입니다.
- A의 F0 기준(단어 하나, 입력 칸 하나만 있어도 차단)을 그대로 쓰면 **모든 쇼핑몰이 막힙니다**(10/30 WEB_OVERLAY.md 5절에서 확인).
- 그래서 단어가 아니라 **"그 페이지가 실제로 로그인·결제·개인정보 페이지라는 증거"**만 봅니다.

### 2-4. 규칙: 넷 중 하나라도 맞으면 그 화면은 건드리지 않음

| 신호 | 기준 | 이유 |
|---|---|---|

### 2-5. 검증

- **단위 시험** `BrowserSensitivityTest` 5개 통과:
  - 11번가 홈 2종은 안 걸림
  - 민감 주소 11개는 걸림, 일반 주소 6개는 안 걸림
  - 로그인 양식은 걸리고 "비밀번호 찾기" 링크만으로는 안 걸림
  - 결제 흔적 2개는 걸리고 1개는 안 걸림
  - 개인정보 4종은 걸리고 대표번호·가격은 안 걸림
- **실제 덤프 재생:** 쇼핑·포털 화면 25장(11번가, 롯데온, 예스24, 네이버, 다음, 나무위키, 올리브영, 무신사, 인터파크, 재현 앱 등)에서 **오탐 0개**
- **로그인 페이지 실측(에뮬레이터 크롬):**
  - 네이버 로그인(`nid.naver.com/nidlogin.login`, 아이디·Password 입력 칸)과 카카오 로그인(`accounts.kakao.com/login`)은 모두 **① 주소로 걸려 아무것도 안 함**.
  - 11번가 로그인 주소는 홈으로 넘어가서(주소창 `m.11st.co.kr/page/main/home`) 걸리지 않았는데, 실제 화면도 홈이라 맞는 결과입니다.

### 2-6. 연결과 한계 (재호·우진 결정 필요)

- **연결:** `SimpleCloseAccessibilityService`에서 트리를 읽은 직후(영상 건너뛰기보다 먼저) `BrowserSensitivity.check(read.nodes, read.screen)`가 null이 아니면 아무것도 안 하고 끝내는 한 줄입니다.
  - 재호가 지금 이 파일을 계속 고치고 있어서 **연결은 하지 않았습니다.**
- **한계와 제안:** 시연 엔진의 `NodeSnapshot`에는 `isPassword`가 없습니다.
  - `SimpleTreeCollector`가 노드를 읽을 때 `node.isPassword`가 true면 그 화면을 건너뛰게 하면 ②보다 정확합니다.
  - 칸에 무엇이 적혔는지는 읽지 않고 표시만 보면 됩니다.
- **질문:** 시연 사이트(11번가, 옥션, 올리브영)는 막지 않으면서, 시연 중 실수로 로그인 화면을 열었을 때 앱이 조용한 게 맞는지 확인 부탁합니다.

## 4. 11/2·11/3 과제 사전 검토 (아직 코드 없음, 의견 요청)

### 4-1. 영상 광고 건너뛰기의 범위 (11/3, `VideoAdSkip`)

- **지금 동작:** 유튜브만이 아니라 **모든 앱·페이지**에서, 팝업을 찾기 전에 먼저 실행됩니다.

- **문제가 될 수 있는 경우:**
  - 쿠팡처럼 상품 목록에 "광고" 표시가 깔린 앱에서 튜토리얼이나 설문의 "건너뛰기"

- **제안:**
  - (a) 유튜브 앱에서는 지금대로 둡니다.
  - (b) 다른 앱에서는 광고 표시가 건너뛰기 버튼과 **같은 묶음(부모) 안이나 바로 옆**에 있을 때만 누릅니다.
  - (c) "광고성"은 광고 표시로 보지 않습니다.
  - (d) B 결정·사기 검사를 먼저 거칩니다.

### 4-2. 글자 없는 이미지 팝업과 강력 모드 (B 리뷰 #68에서 이어짐, 결정 필요)

- **위험:** 이미지에만 글자가 있는 사기 팝업("바이러스 감염!"이 그림으로만 있음)은 OCR이 없어서 판단 불가로 분류되고, 이름 있는 "닫기"가 있으면 강력 모드가 누릅니다. 사기 페이지의 "닫기"는 가짜일 수 있습니다.
- **그런데 실측 반례가 있습니다.** 예스24 광고 시트도 광고 내용이 이미지뿐이라 글자가 없지만, 닫는 게 맞습니다(3-1).
- 글자만으로는 둘을 구분할 수 없어서 두 가지 안을 놓고 고르는 게 맞다고 봅니다.

| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| A (지금 그대로) | 글자 없어도 이름 있는 닫기면 강력 모드가 누름 | 예스24 같은 이미지 광고가 닫힘 | 이미지 사기 팝업의 가짜 "닫기"를 누를 수 있음. 누른 뒤 닫힘 확인에 실패하면 다시 안 누르고 묻기는 함 |

## 6. 같은 창 덮개의 실행 근거와 연속 팝업 (11/2, 제안)

### 6-1. 누르기 직전 B 재판단 (`PrePressRecheck`)

**문제**
- 지금 시연 엔진이 누르기 직전에 다시 보는 것은 두 가지뿐입니다.
  - 팝업 범위가 같은 자리·같은 크기로 그대로 있는지(`rootStillPresent`)
  - 누를 버튼이 같은 자리에서 같은 이름인지(`targetMatches`)
- 그런데 같은 창 덮개(웹 레이어, 바닥 시트)는 페이지와 창을 같이 써서, **범위는 그대로인데 안의 글자만 바뀔 수 있습니다.**
  - 슬라이드 광고가 다음 장으로 넘어가는 경우 (예스24 "8/8", 롯데온 "1/1" 표시)
  - 홍보 단계가 "결제 수단 선택"이나 "수신 동의" 단계로 바뀌는 경우
- 판단(분류)은 처음 한 번만 하고, 실제 누르기는 포커스 이동 등을 거친 뒤에 일어납니다. 그 사이에 바뀐 내용은 보지 않습니다.

**목표:** 누르는 순간의 팝업이 결정·사기·위험 버튼이 없는 팝업이라는 것을 다시 확인합니다. 슬라이드 광고는 막지 않습니다.

**규칙 제안:** 누르기 직전에 팝업 범위만 다시 읽어서 B 분류를 다시 돌리고, 아래 중 하나면 누르지 않고 묻습니다.
1. 지금 보니 **결정이나 사기 의심** (`BECAME_DECISION_OR_SCAM`)
2. 결정 단어가 든 **위험 버튼이 새로 생김** (`RISKY_BUTTON_APPEARED`). 1-4의 홍보 구매 버튼은 제외
3. 종류가 바뀌었는데 그 종류를 지금 처리 방식이 닫지 않음 (`KIND_CHANGED`). 강력 모드는 결정·사기 말고 모두 닫으므로 해당 없음

**왜 글자가 아니라 B 판단을 비교하나:** 글자 요약값(`contentDigest`)이 같은지 보면 슬라이드 광고가 넘어갈 때마다 멈춥니다. 실측한 예스24·롯데온 모두 슬라이드 표시가 있었습니다. 우리가 막고 싶은 것은 "내용이 바뀐 것"이 아니라 "결정이나 위험으로 바뀐 것"입니다.

**검증 (`OverlayExecutionRulesTest`)**
- 슬라이드 장이 바뀌어도 그대로 누름
- 홍보가 결제 수단 선택, 수신 동의 질문, 경품 당첨 문구로 바뀌면 멈춤
- "예약" 버튼이 새로 생기면 멈춤
- "광고만 닫기"에서 광고가 공지로 바뀌면 멈추고, 강력 모드에서는 그대로 누름

**연결 (재호):** `pressAndConfirm`에서 `stillThere` 확인 바로 뒤에 놓습니다.
1. 팝업 범위를 다시 읽어 `SimplePopupAnalysis.build`로 만든 값을 `PrePressRecheck.check(decided, fresh, 지금 닫는 종류)`에 넣습니다.
2. 결과가 null이 아니면 `STALE`처럼 누르지 않고 끝냅니다.
- 다시 읽는 비용은 팝업 범위만이라 작습니다. 재호 F16에서 범위만 읽는 데 약 0.1초였습니다.

### 6-2. 연속 팝업 (`ChainGuard`)

**문제**
- 팝업 하나를 닫으면 다음 팝업이 바로 뜨는 사이트가 많습니다. 11번가는 위쪽 앱 열기 띠와 바닥 시트가 같이 있습니다.
- 지금 시연 엔진에는 **같은 앱에서 자동 닫기를 몇 번까지 할지 제한이 없습니다.**
- 가짜 닫기를 누르면 **다른 레이어가 열리는 광고**도 있습니다. 그러면 새로 뜬 그 레이어도 또 닫게 됩니다.

**목표**
- 광고가 광고를 계속 여는 고리를 끊습니다.
- 우리가 누른 직후 새로 뜬 팝업은 "우리가 연 것일 수도 있다"고 보고 사용자에게 넘깁니다.

**규칙 제안**
1. **한 앱에서 1분에 자동 닫기 3번까지** (`RATE_LIMIT`). 넘으면 묻기로 바꿉니다.
   - 근거: B의 원래 자동 닫기 정책(`DecisionAutoClose`)에서 팀 리뷰를 거친 숫자를 그대로 썼습니다.
   - 정상적인 사이트는 첫 화면에 팝업이 2개 정도라 3번이면 충분하고, 그 이상은 광고 고리일 가능성이 큽니다.
2. **우리가 누른 뒤 1.5초 안에 다른 팝업이 새로 뜨면 묻기** (`OPENED_BY_OUR_PRESS`)
   - 근거: 재호 F20 실측에서 11번가 시트는 닫힌 뒤 0.4초 만에 **같은** 시트로 다시 잡혔습니다. 화면 반응은 1초 안팎이라 1.5초를 경계로 잡았습니다.
   - 같은 팝업이 돌아온 경우는 지금처럼 `PopupMemory.reappeared`가 처리하고, 이 규칙은 **다른** 팝업일 때만 적용합니다.
   - 사람이 직접 누른 뒤에도 적용합니다(그 누르기가 연 팝업일 수 있음). 자동 닫기 횟수에는 세지 않습니다.

**검증 (`OverlayExecutionRulesTest`)**
- 같은 앱 3번 뒤 4번째는 묻기, 다른 앱은 따로 셈, 1분 뒤 다시 가능
- 누른 뒤 0.8초에 다른 팝업이면 묻기, 같은 팝업이면 이 규칙 해당 없음, 1.6초 뒤면 통과
- 사람이 누른 뒤에도 적용

**연결 (재호)**
- 자동 닫기를 결정하기 직전(`decided is AutoClose` 다음)에 `ChainGuard.check(package, popup.root.key, now)`가 null이 아니면 묻기로 바꿉니다.
- 누른 뒤에는 `pressed(..., automatic)`을 부릅니다.

**남은 질문:** 숫자(1분 3번, 1.5초)는 에뮬레이터·시험 기준입니다. LG에서 11번가처럼 팝업 2개가 연달아 뜨는 사이트로 확인이 필요합니다(5절 8번).

### 6-3. 평평한 하단 배너의 재확인 (11/2 갤럭시에서 찾음, 리뷰 요청)

### 8-2. 글자 없는 이미지 팝업은 "앞으로 항상"에서 제외 (수정)

- **근거:** C의 `RememberChoiceRules.offers`에도 이미 "Image only, no words: 다음에 같은 팝업인지 구분할 수 없다"는 같은 이유로 제외가 있습니다. X 경로만 이 규칙을 안 거쳤습니다.
- **규칙 제안(`canRemember`):** 버튼 이름 말고 자기 글자가 있는 팝업만 "앞으로 항상"을 제안합니다.
- **4-2와의 관계:** 4-2 A안(이미지 팝업 강력 모드 유지)과 충돌하지 않습니다. 한 번 닫는 것과 앞으로 계속 닫는 것은 위험이 다릅니다.

### 8-3. 자동 닫기 스위치를 꺼도 기억한 팝업은 닫힘 (수정)

- **문제:** 기억한 팝업 경로(F22)는 처리 방식·스위치를 보지 않습니다. 사용자가 "자동 닫기"를 꺼도 기억한 팝업은 계속 눌립니다.
- **왜 문제인가:** 스위치를 끈 사람은 앱이 혼자 누르지 않기를 기대합니다. AGENTS 6-2도 자동 실행의 전제로 스위치 동의를 듭니다. 원래 B 정책의 반복 조건 1번도 "자동화 설정이 켜져 있음"입니다.
- **규칙 제안:** 기억한 팝업도 `autoCloseKinds(live = true)`가 비어 있지 않을 때만 혼자 누릅니다. 기억 자체는 지우지 않습니다. 스위치를 다시 켜면 그대로 동작합니다.
- **질문:** 재호 P04 시험은 스위치를 켠 상태라 영향이 없습니다. "스위치 꺼도 기억한 것은 닫혀야 한다"는 의도였다면 말해 주세요.

### 8-4. 기다릴 초를 C에 넘기기 (11/3, `VideoAdSkip.waitSeconds`)

- **문제:** 지금은 "기다리는 중"만 알고, 몇 초인지는 C에 넘기지 않습니다. 화면을 볼 수 없으면 광고가 언제 끝나는지 모릅니다.

  - 한 글자 안에 건너뛰기 말과 시간이 같이 있고, 결정 단어가 없고, 1~300초일 때만 읽습니다.
  - 값이 서로 다르면 null입니다. 추측하거나 우리가 세지 않습니다.
- **검증:** "5초 후 건너뛰기"는 5, "Skip ad in 10s"는 10, 나머지 5종(건너뛰기만, 시작 문구, 결정 단어, 값 2개, 화면 밖)은 null.
- **연결(재호):** `VideoAdSkipResult.Waiting`일 때 값을 받아 C가 한 번만 말합니다. 실제 유튜브 문구로 되는지는 LG에서 확인이 필요합니다.

### 8-5. 질문: 로그인 홍보 팝업의 정책

### 8-6. 알아 둘 것: 기억 키는 기기 키를 쓰지 않음

- 시연 엔진의 기억(`RememberedPopups`)은 D의 Room·기기 키(HMAC) 지문이 아니라 **평범한 SHA-256**을 앱 전용 저장소에 둡니다. 화면 글자 원문은 없고 외부 전송도 없습니다.
- 다만 짧은 문구는 해시만으로 추측할 수 있고, 중간발표 질문 대비에서 "기기 안 키로 만든 지문"이라고 설명한 것과 다릅니다.
- **제안:** 시연에는 지장이 없어서 그대로 두되, 발표에서는 이렇게 말하지 않도록 합니다. 시간이 남으면 D의 `AndroidKeystoreHasher`로 바꿉니다.

## 10. 연속 팝업에서 다음 팝업을 "닫기 실패"로 보는 문제 (제안, 리뷰 요청)

**문제.** 갤럭시(SM-M446K, 11/2, c279ee3)에서 재현 앱 P12를 돌렸습니다. 쿠폰이 닫힌 뒤 공지가 같은 자리에 뜨자 `CLOSED_CONFIRMED`가 아니라 `NOT_CLOSED_REAPPEARED`, `AUTO_CLOSE_FAILED_ASKED`가 나왔습니다.
- 사라진 쿠폰을 닫지 못했다고 안내하고, 쿠폰 내용으로 선택 창을 띄웁니다.
- 잘못 누르는 일은 아니지만 연속 팝업 안내가 틀립니다.

**원인.** `PopupMemory.reappearance`는 글자나 자리가 하나라도 같으면 같은 팝업으로 봅니다. 다음 팝업의 "닫기"가 이 조건을 만족합니다.

**제안 규칙.** 닫은 팝업과 지금 팝업에 모두 고유 문구가 있고, 닫은 팝업의 고유 문구가 하나도 남지 않았으면 다른 팝업으로 봅니다.
- 고유 문구는 버튼과 닫기 후보 이름을 뺀 글자입니다. 이미지 광고의 설명 글자는 포함합니다.

**남는 위험.** 누른 뒤 문구만 전부 바뀌어 같은 자리에 남는 팝업은 "닫혔다"고 안내할 수 있습니다. 1.5초 안에 다시 찾으면 묻기로 넘어가지만, 안내 한 번은 틀립니다.
- 이 경우를 찾을 수 있게 `CLOSE_NEXT_POPUP_NOT_BACK` 코드를 남깁니다(재호 요청). 실기기 로그에 이 코드가 나오면 실제로 다른 팝업이었는지 함께 봐야 합니다.
