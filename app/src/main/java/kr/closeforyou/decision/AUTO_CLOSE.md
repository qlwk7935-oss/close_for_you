## 1. 한 문장 규칙

**위험 신호는 넓게, 닫을 이유는 좁게, 누를 버튼은 하나만, 한 팝업은 세션에 한 번만.**

- **위험 신호(결정·사기·불확실):** 어디서 봤든 하나라도 있으면 묻는다. 트리·OCR·팝업 밖 모두 해당한다.
  - 띄어쓰기를 지운 형태, 전각 문자(Ａ), 보이지 않는 문자(U+200B, U+3164 등)로 숨긴 단어도 찾는다.
- **닫을 이유(쿠폰·광고·공지):** 팝업 안의 접근성 트리 글자만 인정한다. 띄어쓰기를 지워서 단어를 만들어 내지 않는다("보 안경"은 보안이 아니다).
- **누를 버튼:** 라벨 계약상 CLOSE/SKIP인 E1/E2 버튼이 정확히 하나일 때만 정해진다.
- **반복:** 같은 팝업이 세션 안에 다시 나오면 묻는다. 반복해서 닫는 것은 F12 [앞으로 항상 닫기]로만 한다.

## 2. 실제 파이프라인에서 B가 받는 것 (A 코드 기준, 에뮬레이터로 확인)

| A 단계 | 조건 | B가 받는 것 | 자동 닫기 |

| 그 외 | — | 트리 글자 + (필요하면) 팝업 영역 OCR, `INCOMPLETE_EVIDENCE` 표시 | 4절 조건으로 판단 |

결과적으로:
- R1("가입하면 쿠폰" 허용)은 A 요약 단어가 없는 문장(가입·로그인 계열)에서만 효과가 있다. "결제하면 할인"(P18)은 A 단계에서 이미 결정이 된다.
- 실제 앱 화면 어디에든 "고객센터", "회원", "로그인", "카드", "이름" 같은 글자가 있으면 화면이 통째로 차단된다. 그런 화면은 자동 닫기 대상이 아니다. 차단 범위는 A 정책이다(7절 질문 6).

## 4. 자동 닫기 승인 조건 (`DecisionAutoClose.evaluate`, 하나라도 걸리면 승인 없음)

입구는 `evaluate(snapshot, detection, analysis, context, preset)` 하나다.
- 팝업 범위(5절)를 **먼저** 적용한다.
- 세 토큰이 다르면 `STALE_SCREEN`으로 막는다.

| # | 조건 | 막힐 때 코드 | 그 뒤 처리(제안) |
|---|---|---|---|
| 1 | 프리셋이 하나라도 켜져 있음 (결정·모름은 넣어도 무시) | `PRESET_OFF` | 지금처럼 묻기 |
| 2 | 종류가 COUPON·ADVERTISEMENT·NOTICE이고, 이미 USER_DECISION으로 표시된 분석이 아님 | `KIND_NEVER_CLOSED` | 묻기 (사기는 경고) |
| 3 | 프리셋이 그 종류를 닫음 | `KIND_NOT_IN_PRESET` | 내용 안내만 |
| 4 | 그 종류가 트리 글자만으로도 나옴 | `NOT_TREE_EVIDENCE` | 안내 |
| 5 | 사용자 선택·기억 규칙이 없음 (있으면 기존 정책이 판단) | `OTHER_PATH` | 기존 정책 |
| 6 | 토큰이 현재 화면과 같음 | `STALE_SCREEN` | 새 관측 |
| 7 | 사용자가 조작 중이 아님 | `USER_INTERACTION` | 대기 |
| 8 | 결과를 안내할 수 있음 | `FEEDBACK_UNAVAILABLE` | 묻기 (조용히 닫지 않음) |
| 9 | 모의 데이터가 아님 (`MOCK_ONLY`) | `MOCK_DATA` | — |
| 10 | 검증된 E1/E2 CLOSE가 **정확히 1개** → 그 버튼. CLOSE+SKIP이 같이 있으면 CLOSE (P17) | `AMBIGUOUS_TARGET` (2개 이상) | 묻기 |

| 16 | 같은 팝업을 이번 세션에 이미 자동으로 닫은 적이 없음 | `CLOSED_BEFORE` | 묻기. 반복은 F12 기억 규칙으로 |
| 17 | 같은 앱에서 누른 뒤 앱 밖으로 나간 적이 없음 (가짜 닫기) | `APP_PAUSED` | 그 앱은 세션 동안 묻기 |

**"검증된 버튼"** (기존 정책과 같은 함수 `isVerifiedTarget`)
- 라벨이 있고, E1/E2이고, 역할이 CLOSE/SKIP이다.
- **라벨 자체가** `ButtonLabelRules`상 그 역할이다.

그래서 X, 라벨 없음, E3·E4, "오늘 하루 닫기", "닫기 전 저장", "확인", "자세히 보기"는 절대 대상이 되지 않는다.

**결과 처리** (`DecisionActionPolicy.onActionResult` → `onResult`, A가 모든 결과를 넘김. 계약 v2 `ClickOutcome` 기준)

| A 결과 | B가 하는 일 |
|---|---|
| 누르지 않음 (NOT_EXECUTED·BLOCKED·STALE, attempted=false) | 기록을 풀어 준다. 횟수 제한에도 세지 않는다 |
| 성공 = `attempted` + `MECHANICAL_SUCCESS` + `CLOSED_CONFIRMED` (팀 기준 10/25, A #42·C PressSuccess와 같음) | 그 팝업은 세션 동안 "이미 닫음"(16). 다시 뜨면 묻는다. 반복은 F12에서 사용자가 허락했을 때만 |
| 그 밖에 누른 뒤 결과 전부: `STILL_PRESENT`·`UNKNOWN`·관측 없음, 실패·결과 불명인데 팝업이 사라짐, attempted=true인 STALE, 30초 무응답 | 그 팝업은 세션 끝까지 자동 금지. 셋 중 하나만으로는 닫힘으로 보지 않는다 |
| `LEFT_APP` (가짜 닫기) | 그 팝업과 그 앱 전체를 세션 동안 자동 금지. 결과가 늦게 와도, 사용자가 직접 고른 누르기여도 적용한다 |

**A 적격 근거:** `PopupAnalysis.autoEligibility`에 다섯 검사가 다 있고, 같은 토큰이고, **원본 화면 수집 시각** 후 5초 안이어야 한다(#38). B 배선은 근거의 수집 시각이 그 화면과 다르면 버린다. 아니면 `NOT_AUTO_ELIGIBLE`로 묻는다.

**정책 출력** (`DecisionActionPolicy`, 계약 v2)

| 상황 | authorization | next | source |
|---|---|---|---|
| 프리셋 조건 전부 통과 | ALLOW_ONCE | EXECUTE | PRESET |
| 결정·사기 의심 | DENY | DENY | (누가 요청했든) |
| 닫기 버튼 대기, 결과 대기, 사용자 조작 중, 화면 바뀜 | 그대로 | WAIT | PRESET 등 |
| 프리셋이 안내만 하는 종류, 트리 근거 부족, 공지인데 버튼 없음 | 그대로 | ANNOUNCE | PRESET |
| 그 밖 (버튼 여러 개, 전에 실패, 이미 닫음, 1분 3회, 앱 이탈, 적격 근거 없음) | 그대로 | ASK | PRESET |
| 프리셋 없음 (기본) | 지금과 같음 | ASK (결정이면 DENY) | 없음 |
| 사용자 선택 / 기억 규칙 | 지금과 같음 | 위와 같은 규칙 | USER_CHOICE / REMEMBERED_RULE |

- 기록은 메모리에만 있고 화면 글자는 담지 않는다. 키는 패키지 + A 구조 지문이다.
- 배치가 같은 팝업끼리는 기록을 같이 쓴다. 한쪽이 실패하면 다른 쪽도 막히는데, 조심스러운 쪽이다.

## 5. 팝업 범위 (`DecisionPopupScope.texts`)

- **새 창(Dialog 창):** A가 활성 창 트리만 모으므로 그대로 쓴다.
- **같은 창 덮개:** Dialog 노드가 정확히 1개면(후보 찾기와 같은 기준) 아래 글자만 남긴다.
  - 그 Dialog 하위 노드가 **같은 위치에 같은 글자로** 가진 트리 글자
  - Dialog 영역 안의 OCR 글자
  - **팝업 밖이라도** 결정·사기·불확실 신호 (절대 빼지 않음)
- **팝업 밖에서 빼는 것:** 공지 가드 단어("공지사항" 탭)와 평범한 글자("무엇을 찾으세요?", "이벤트 참여하기").
- **범위를 못 정한 화면:** 그대로 둔다. 이런 화면에는 후보도 없어서 닫을 일이 없다.

## 8. B 처리 결과를 C로 넘기는 경로 · 팝업 제목 (계약 v3 #45로 반영, 제목 개인정보 제외 #50)

재호 지적: 프리셋이나 기억으로 B가 바로 처리한 결과를 C가 받을 경로가 계약에 없다.

**① 처리 보고** (A가 C에 보냄. 새 포트)

    data class HandlingReport(
        val token: SnapshotToken,
        val classification: PopupClassification,
        val decision: ActionDecision,     // source, next, reasons
        val result: ActionResult?,        // EXECUTE였을 때만, outcome 포함
        val title: String?,               // ② (선택)
    ) // toString은 가림, 저장·로그 금지

- A의 조립 코드가 `decide → (EXECUTE면) execute → policy.onActionResult` 다음에 C에 넘긴다.
- C는 `next`와 `outcome`으로 안내 문장을 고른다. 이미 순수 함수로 준비돼 있다.
  - "닫았어요"는 `CLOSED_CONFIRMED`일 때만
  - WAIT은 한 번만
  - DENY+사기는 경고
- ASK면 지금 선택 창 흐름을 그대로 쓴다.

**② 팝업 제목** (`PopupAnalysis.title: String? = null`, B 배선이 채움)

- 규칙: 팝업 범위 안의 트리 글자 중 **첫 번째로, 닫기 후보의 라벨도 결정·사기 문구도 아닌 것**. 없으면 null.
- 자르기는 C가 한다. 화면 글자라서 말로만 쓰고 로그·저장은 하지 않는다.
- B가 정하는 이유: 범위 판정과 같은 기준이라 뒤 페이지 글자가 제목으로 읽히지 않는다.

**③ 묶음 안내** ("광고 2개, 쿠폰 1개를 닫았어요"): C가 2초 동안 `HandlingReport`를 모아서 한다.
