## 1. 결론

**C 창 결합은 성공한다. 그 뒤 C 창이 아닌 다른 창에서 온 이벤트 1개를 A가 화면 변화로 보고 토큰을 무효화하는 것이 직접 원인이다.** 그 다른 창이 무엇인지(대상 앱 P01 창인지, 시스템 창인지)는 아직 확정하지 못했다.

1차 결론("① 순서 — C 창 id를 몰라서 C 창 이벤트를 놓친다")은 **C 계약 문서의 방식**(show 직후와 `TYPE_WINDOWS_CHANGED` 때만 `update()`)을 따를 때의 이야기였다. **A V5는 그 방식을 쓰지 않는다.** 그래서 1차 결론은 A 통합의 원인이 아니다. 아래에 정정한다.

### A V5가 실제로 하는 일 (코드로 확인)
`accessibility/integration/ServiceChoiceIntegration.kt`, `OwnedOverlayEventPolicy.kt`, `CloseForYouAccessibilityService.kt`
1. `present()` 직전: `readOwnedIds()`로 "C 창처럼 보이는 창" 집합(before)을 읽는다.
   - 조건: 종류 `ACCESSIBILITY_OVERLAY`, 기본 디스플레이, 루트 노드의 패키지가 우리, 루트의 창 id가 그 창과 같음, 제목이 고정 제목.
2. `SHOWN`이면 `binding.expect(before, 토큰, 세대)`를 한다. **C의 `OwnOverlayWindowTracker.update()`는 쓰지 않는다.**
3. 이벤트마다(C 창이 `SHOWING`일 때) 이벤트를 종류별로 나눈다.
   - 내용 변화 / 창 상태 변화 / 포커스 / `WINDOWS_CHANGED` 중 추가·크기·층·제목 변화만: 그 순간 `readOwnedIds()`를 다시 읽어 결합을 검사한다.
   - 그 밖(클릭·터치·스크롤, 창 제거·활성 변화가 섞인 `WINDOWS_CHANGED` 등): 바로 "무시 안 함"이 된다.
4. 결합 검사 (`OwnedOverlayBinding.matches`)
   - 아직 결합 전: (지금 집합 − before)가 정확히 1개이고 이벤트 창이 그 창이면 **결합**하고 무시한다.
   - 결합 후: 이벤트 창이 결합된 창과 다르면 `BOUND_EVENT_WINDOW_MISMATCH`로 거부한다. 같아도 그 창이 지금 목록에 없으면 거부한다(`BOUND_WINDOW_NOT_LIVE`).
5. 무시되지 않은 이벤트는 서비스에서 **그대로 `invalidate(EVENT)`** 된다. 그러면 C 창이 `dismiss`되고, 재질문은 금지다.
6. A의 디버그 로그(`A_OverlayEvent`)는 표시 1회당 **처음 거부된 이벤트 1개만** 남긴다. 남기는 것은 `EVENT`(종류), `REASON`, `BINDING_DETAIL`뿐이고, 어느 창이었는지는 남기지 않는다.

### 우리 7회 실측과 우진 로그가 맞는 이유
- A는 이벤트 때 창 목록을 다시 읽는다. 이것은 1차 문서의 "제안 1"과 같은 방식이다.
- 우리 7회에서 **C 창 이벤트를 처리하는 시점에는 7/7 모두 C 창이 이미 목록에 있었다.** 그래서 이벤트 때 다시 읽는 판정(`ownFresh`)은 C 창 이벤트를 전부 맞혔다.
  - 그렇다면 A도 C 창의 첫 이벤트에서 결합에 성공한다.
  - 우진 로그의 `BOUND_EVENT_WINDOW_MISMATCH`("이미 결합된 C 창과 이벤트 창이 다름")도 결합이 적어도 한 번 성공했다는 뜻이다.
- 같은 7회에서 C 창에서 온 이벤트(패키지=우리)는 **7/7 모두 이벤트 창 = 목록의 C 창**이었다. C 창이 자기 이벤트를 다른 창 id로 보내는 일은 없었다(1차의 ② 아님 유지).
- 따라서 `BOUND_EVENT_WINDOW_MISMATCH`를 일으킨 이벤트는 **C 창이 아닌 창**에서 온 내용·상태·포커스 이벤트, 또는 그 창의 추가·크기·층·제목 변화이다.
  - 그 이벤트는 A 설계대로 "화면이 바뀜"으로 처리되어 무효화된다.
  - 이것은 A 결합 로직의 오판이 아니라 **무효화 범위**의 문제다.

### 이전 C 창의 "제거" 이벤트 (A V5 기준으로 다시 봄)
- 2~7회에는 show 직후 목록에 방금 지운 이전 C 창이 남아 있었다. 그 창의 `WINDOWS_CHANGED(제거)`는 새 C 창 이벤트보다 먼저 처리됐다.
- A V5 `readOwnedIds()`는 루트가 없는 창을 빼므로 결합에는 영향이 없다.
- 그러나 A V5는 "제거"가 섞인 `WINDOWS_CHANGED`를 무시하지 않는다(`MASK_UNSUPPORTED`). 그래서 **이전 C 창을 지운 직후 새 C 창을 띄우는 경우**에는 이 이벤트로 새 토큰이 무효화된다.
- #29(첫 표시, `BOUND_EVENT_WINDOW_MISMATCH`)의 원인은 아니다. 연속 팝업 때 같은 증상이 날 수 있으니 기록해 둔다.

## 4. 제안 (안전장치를 약하게 하지 않는 것)

### 제안 1 (먼저, A) — 거부된 이벤트가 "어느 창"인지 enum으로 남기기
- `OverlayEventDiagnostic`에 창 id 원값 대신 **관계 enum**을 하나 추가한다.
  - 예: `TARGET_WINDOW`(토큰의 대상 앱 창), `SYSTEM_WINDOW`, `OTHER_APP_WINDOW`, `INPUT_METHOD`, `OTHER_OVERLAY`, `NOT_IN_LIST`
- 지금 로그의 `EVENT=` 값(내용/상태/포커스/창 변화)과 합치면 원인이 바로 확정된다.
- 위험: 없음. 기록만 늘고 판단은 그대로다. 누가: A.
- 우진에게 먼저 부탁: 이미 남은 로그의 `EVENT=` 값.

### 제안 2 (원인이 대상 앱 창이면, A·B) — 대상 앱 창이 조용해진 뒤에 띄우기
- 대상 창의 변화가 일정 시간 없을 때만 `present()`한다. 또는 띄우기 직전에 대상 창 상태를 다시 확인한다.
- 대상 앱이 바뀌면 무효화하는 규칙(AGENTS 6장 7번)은 **그대로**다. 띄우는 시점만 늦춘다.
- 위험: 안내가 조금 늦어진다. 계속 움직이는 팝업(영상 등)에서는 영영 안 뜰 수 있으므로 상한과 안내가 필요하다. 누가: A(감지·현재성), B(분류 시점).

### 제안 3 (원인이 시스템 창이면, A·B 결정 사항) — 무효화 범위
- 상태 표시줄 같은 시스템 창의 변화까지 대상 앱 토큰을 무효화할지는 **A·B 안전 설계 결정**이다.
- C는 범위를 줄이자고 요구하지 않는다.
- 줄인다면 조건을 붙여야 한다. "대상 앱 창과 겹치지 않는 시스템 창의 내용 변화만" 같은 식으로 좁게 정하고, 사용자 조작·대상 앱 변화·민감 화면 검사는 그대로 둔다.
- 위험: 대상 앱 위에 뜬 시스템 대화상자(권한 요청 등)를 놓칠 수 있다. 그래서 겹침 검사가 꼭 필요하다.

### 제안 4 (C) — C 계약 문서·트래커 정리
- `OwnOverlayWindowTracker`의 "show 직후 + `WINDOWS_CHANGED` 때 `update`" 방식은 실측상 첫 C 창 이벤트를 놓친다(7회 중 6회).
- A V5처럼 "판정할 이벤트 때 다시 읽기"로 계약 문서를 고치거나, A가 쓰지 않는 트래커를 `@Deprecated` 처리한다.
- C main 코드 변경이므로 **별도 PR**로 한다.

### 하지 말 것
- 패키지명만으로 C 창 판단, show 뒤 일정 시간 모든 이벤트 무시, 무효화 끄기, 무효화 후 재질문 허용

## 5. 하지 못한 것·한계
- **A V5 빌드 + A 서비스로 P01 실제 재현은 하지 못했다.**
  - A V5 빌드(스크래치 worktree, C debug 진단 파일만 복사)는 성공했다.
  - 에뮬레이터에서 A 서비스를 켜고 A 동의 설정을 debug 저장소에 쓴 뒤 P01을 여는 실행은 Claude Code 자동 권한 검사가 막았다(사유 "Security Weaken"). 우회하지 않았다.
  - 그 직후 A 서비스를 끄고 A 설정 파일을 지워 원래대로 되돌렸다.
- C 단독으로 "P01이 뜬 지 약 1초 뒤 표시"하는 추가 관측을 6회 시도했으나 모두 **무효**다. 이유는 에뮬레이터 부팅 직후 부하(load 30, 시스템 UI 응답 없음 대화상자), C 창 추가 0.4~3.7초, C 창이 P01이 아니라 미리보기 화면 위에 뜬 것이다. 표에 넣지 않았다.
- 시험 서비스와 A 서비스의 남은 차이: `canTakeScreenshot`·`isAccessibilityTool`, A의 OCR·분류 처리 시간(이벤트 처리 간격이 달라짐). 실기기(LG, 갤럭시 S26)는 미검증이다.

- 끝나면 접근성 설정을 원래 값으로 되돌린다.

## 8. 실제 A 통합 재현 (10/23 밤) — 원래 계획의 "3. 실제 A 통합 재현"

> 에뮬레이터 `Pixel_8`(API 37)만 썼다. 실기기(LG)는 건드리지 않았다. 클릭은 0회다(A 게이트 비실행 그대로).
> 빌드: 스크래치 worktree, 우진 진단 브랜치 `origin/diag/issue29-event-cause-v2`(4f67ee6, V5 + 거부 창 분류 enum) + **로컬 진단 패치**(커밋·push 안 함, worktree 삭제함).
> A 설정: 사용자 승인 뒤 A 서비스 켜기, A 앱 화면에서 접근성 정보 수집 동의, 허용 앱은 재현 앱 하나, 분석 시작. 캡처·OCR 동의는 끔. 끝난 뒤 앱 데이터 삭제, 접근성 설정을 원래 값(TalkBack만)으로 되돌림.

### 8.1 결론 (쉽게)
- **원인 창은 하나가 아니다.** A는 C 창이 떠 있는 동안 C 창이 아닌 창의 이벤트가 하나만 와도 무효화한다. 그런데 화면에는 늘 "무해한" 이벤트가 온다. 실측에서 C 창을 닫게 만든 것은 아래 네 가지다.
  1. **대상 앱(P01) 창 전환의 마무리 이벤트 — TalkBack 켬에서 "뜨자마자 사라짐"의 원인.** 표시 후 3~21ms에 처리된다. 실제로는 표시 전(54~732ms 전)에 일어났지만, A가 캡처·분석하는 동안 처리가 밀렸다.
     - 사라진 이전 창(스플래시로 추정)의 `WINDOW_STATE_CHANGED` → `NOT_IN_LIST`, `OWNED_WINDOW_UNCONFIRMED`
     - 대상 창의 `WINDOWS_CHANGED`(`WINDOWS_CHANGE_ACTIVE`=128) → `TARGET_APP`, `MASK_UNSUPPORTED`
     - TalkBack이 P01 대화상자로 옮긴 접근성 포커스 `TYPE_VIEW_ACCESSIBILITY_FOCUSED` → `TARGET_APP`, `FOCUS`, `BOUND_EVENT_WINDOW_MISMATCH` (우진 로그와 같은 사유)
  2. **상태 표시줄(시스템 창, 화면 위 띠)의 내용 변화.** `CONTENT_CHANGED`. 바뀐 종류는 설명(4)·글자(2)·하위 트리(1)다. 표시 후 0.1~16초 사이에 수시로 온다. 위치를 기록한 5건은 모두 `TOP_STRIP`이었고, 대상 창과 겹치지 않았다.
  3. **5초 TTL.** 이벤트가 하나도 없어도 C 창은 캡처 후 5초(표시 후 약 4.9초)에 `CAUSE=TTL`로 닫힌다. 기준선 11회 표시 중 7회가 이렇게 끝났다. TalkBack이 안내를 다 읽기 전에 닫힐 수 있다.
  4. **한 번 무효화되면 다시 뜨지 않는 경우가 있다.** 다시 수집해도 F1이 `NO_POPUP/UNCHANGED`이면 재표시가 없다(R6 등). 또 TalkBack 켬에서는 이벤트가 연달아 오면 대기 중인 캡처가 모두 취소돼 **아예 감지되지 않는** 회차가 있었다(R14·R21·R22·R30).
- 1차 문서의 "후보" 표 중 **대상 앱 창**과 **시스템 창** 둘 다 맞았다. TalkBack 켬에서는 대상 앱 창(1번), TalkBack 끔에서는 시스템 창(2번)과 TTL(3번)이 주원인이었다.

### 8.2 진단 패치 (로컬, A 판단 변경 없음)
- `OwnedOverlayTracker.shouldIgnore` 앞뒤에 로그 한 줄(`C29Local`)을 붙였다. C 창 표시 뒤 이벤트 40개까지 남긴다.
- 남긴 값은 표시 후 경과 ms, `eventTime`과 표시 시각의 차, 이벤트 종류, `contentChangeTypes`, `windowChanges`다.
- 그 밖에 우리 패키지 여부·대상 패키지 여부·대상 창 여부(bool), 소스 노드 유무(bool), 창 분류(우진 enum), 창 위치(`TOP_STRIP/BOTTOM_STRIP/OTHER/NONE`), 원래 판정, 무시 여부를 남겼다.
- 캡처 시각은 `CAPTURED;AGO_MS`, 표시 시각은 `SHOWN`이다. 둘 다 uptime 값을 100000으로 나눈 나머지만 남겼다.
- 창 id·패키지·글자 원값은 남기지 않았다.

### 8.4 좁은 수정안을 로컬로 적용해 다시 잼 (TalkBack 켬)
적용한 면제는 아래 세 가지뿐이다. 클릭·스크롤·터치·글자 입력, 대상 창 내용 변화, 창 제거는 그대로 무효화된다.
- (b) 시스템 창(`TYPE_SYSTEM`)의 `CONTENT_CHANGED` 중 바뀐 종류가 글자·설명·하위 트리뿐이고, 그 창이 대상 창과 겹치지 않을 때 → 무시
- (c) `TYPE_VIEW_ACCESSIBILITY_FOCUSED` / `FOCUS_CLEARED` → 무시. 화면 변화가 아니다. 실행 직전 재확인(AGENTS 6장 5번)은 그대로다.
- (d) `eventTime`이 표시보다 앞서고 지금 창 목록에 없는 창의 이벤트 → 무시. A 정식안은 "스냅샷 수집 시작 시각보다 앞선 이벤트"로 바꿔야 한다.
- 이벤트를 더 보려고 **TTL만 관측용으로 30초**로 늘린 빌드도 썼다(R12~). TTL 결정은 A·B 몫이다.

| 회 | TTL | 결과 |
|---|---|---|
| 9, 10 | 5초 | 이벤트 거부 0, TTL로 닫힘 |
| 11 | 5초 | 시스템 창 CCT=1로 2번 닫힘. 이때 (b)는 글자·설명만 면제했다 → 하위 트리를 추가 |
| 12 | 30초 | **29.8초 유지** (TTL). 시스템 위 띠 3건 면제 |
| 15, 23, 24 | 30초 | 14초 확인 시점까지 유지 (면제 0~1건) |
| 13, 16, 20, 25, 26, 29 | 30초 | 표시 후 7~21ms에 대상 창 `WINDOWS_CHANGE_ACTIVE`로 닫힘 (면제 안 함) |
| 14, 21, 22, 30 | 30초 | 표시 안 됨 (캡처가 모두 대기 중 취소) |

- 대상 창 ACTIVE 이벤트와 캡처 시각의 차(캡처 시각을 아는 3회): +22ms(R25), −25ms(R26), +6ms(R29). **캡처와 거의 같은 순간에 대상 창 활성화가 끝난다.** 캡처 뒤에 일어난 경우가 있으므로 무조건 면제하면 안 된다.

### 8.5 안전 회귀 (면제 적용 빌드)
- C 창이 떠 있을 때 재현 앱을 다른 장면(P02)으로 새로 열었다(클릭 없음, `am start` 새 작업).
- 유효 3회(R19·R27·R28) 모두 무효화됐고 C 창이 사라졌다.
  - 사유: 대상 창 제거 `WINDOWS_CHANGED`(WCH=2) 또는 대상 패키지의 다른 창 `CONTENT_CHANGED`
- R17·R18은 같은 Activity가 재사용돼 화면이 바뀌지 않아 무효다. R29·R30은 변경 전에 이미 닫혔거나 표시되지 않아 무효다.

### 8.6 A에 제안 (안전장치를 약하게 하지 않는 것만)
1. **(b) 상태 표시줄 내용 변화 좁게 제외** — 근거: 기준선·수정 빌드에서 반복 관측. 조건은 시스템 창, 내용 변화 종류가 글자·설명·하위 트리뿐, 대상 창과 안 겹침이다. 창 추가·제거, 겹치는 시스템 창(권한 대화상자 등)은 계속 무효화한다.
2. **(c) 접근성 포커스 이동은 무효화하지 않기** — TalkBack 사용자는 팝업 내용을 읽으려고 포커스를 옮긴다. 지금은 그 순간 질문이 사라진다. 화면 변화가 없으므로 토큰은 유지하고, 실행 직전 재수집·재확인은 그대로 둔다. A·B 결정.
3. **(d) 캡처보다 앞선 이벤트는 이미 반영됐다고 보기** — `event.eventTime < snapshot 수집 시작 uptime`일 때만. 늦게 처리될 뿐 캡처 전에 일어난 이벤트다.
4. **대상 창 전환이 끝난 뒤 캡처** — 가장 큰 남은 원인이다(면제 빌드 표시 10회 중 6회). 캡처 시점에 대상 창이 active·focused가 아니면 그 캡처로 띄우지 않고 다음 이벤트를 기다리기, 또는 표시 직전 짧게 재수집해 창 집합(active 포함)이 같을 때만 띄우기. 무효화 규칙은 그대로 두고 **띄우는 시점**만 늦춘다.
5. **TTL과 질문 창 수명 분리** — 지금은 증거 TTL 5초가 끝나면 질문 창도 닫힌다. 질문 창은 화면이 그대로인 동안 유지하고, 사용자가 고르면 A가 다시 수집·검증해 일치할 때만 진행하는 방식을 제안한다(6장 5·7번 유지). A·B·C 합의 사항이다.
6. (참고) 감지 누락 — TalkBack 켬에서 연속 이벤트로 대기 캡처가 다 취소되면 다음 트리거가 없다. A 감지 영역이다.

### 8.7 한계
- 에뮬레이터 1대, 재현 앱 P01만 봤다. 실기기(LG·갤럭시)는 미검증이다.
- TalkBack 켬에서 사람이 스와이프로 C 창을 탐색하는 경우(터치 상호작용 이벤트)는 시험하지 않았다(클릭·조작 금지). 이 경우도 지금 규칙상 무효화될 가능성이 크다.
- (d)의 "표시 시각" 기준은 실험용이다. 정식 기준은 수집 시작 시각이어야 한다.
- 부팅 직후 시스템 응답 없음 창 때문에 에뮬레이터를 1회 재부팅했다.
