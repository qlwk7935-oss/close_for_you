# `ExtractedText` 노드 경로 추가가 F12 지문에 주는 영향 (D 검토 메모)

담당: 동준/D. 우진(A)이 "`ExtractedText`에 노드 경로를 붙이는 건 공통 계약과 지문에 영향이 있으니 A·B·D가 따로 정하자"(10/22)고 한 논의용 자료입니다. **코드 변경은 없습니다.** 아래 내용은 `DeviceKeyedFingerprintProvider` 코드를 읽고 정리한 것이며, 실측으로 확인한 것은 아닙니다.

## 1. 지금 D 지문이 쓰는 입력

| 지문 | 입력 |
|---|---|
| 본문(`closeforyou.rule.content.v1`) | 스냅샷의 **모든** 노드 글자·설명(노드 경로와 함께) + `analysis.texts` 전부(트리·OCR, 출처·위치 순 정렬) |
| 구조(`structure.v1`) | 창 종류, 모든 노드의 경로·클래스·리소스 ID·클릭·동작, 닫기 후보들의 역할·근거·경로·상대 위치, 글자 출처 목록 |
| 대상(`target.v1`) | 대상 버튼의 역할·근거·리소스 ID·라벨·**노드 경로**·클래스·설명·상대 위치 |

- 노드 경로는 이미 스냅샷 노드와 대상에서 쓰고 있습니다. `ExtractedText`에 경로 칸이 생겨도 **D가 그 칸을 읽지 않으면 지문은 그대로**입니다.
- 원문은 저장하지 않고 기기 키 HMAC 입력으로만 씁니다.

## 2. 지금 구조에서 생기는 일 (P13 같은 화면)

- A 스냅샷에 뒤 화면 노드가 함께 들어오면, 뒤 화면 글자도 본문 지문에 들어갑니다.
- 그래서 팝업은 같아도 뒤 화면 글자만 바뀌면 기억이 맞지 않습니다. **놓치는 쪽(안전한 쪽)** 오류입니다. 다른 팝업을 같은 팝업으로 잘못 보는 일은 생기지 않습니다.

## 3. 경로가 생기면 D가 할 수 있는 것 (선택)

- 팝업 영역 글자만 본문 지문에 넣어, 뒤 화면 변화에 덜 흔들리게 할 수 있습니다.
- 다만 "팝업 영역"을 누가 정하는지가 먼저 필요합니다(A가 팝업 루트 경로를 주거나, B 후보 경로의 공통 조상).
- **잘못 자르면 위험한 쪽 오류**가 됩니다. 팝업 본문 일부가 빠지면 날짜만 다른 공지 두 개가 같은 지문이 될 수 있습니다(N03~N06 재사용 금지 위반).

## 4. 지문 입력을 바꾸면 생기는 일

- 본문 지문 입력이 바뀌면 도메인을 `content.v2`로 올려야 하고, **기존 기억은 전부 맞지 않게** 됩니다.
- 처리 방법: 규칙 스키마 버전(`CURRENT_RULE_SCHEMA_VERSION`)을 2로 올리면 옛 규칙은 C 목록에서 "꺼짐"으로 보이고 만료 뒤 `cleanUp`이 지웁니다. 또는 버전은 두고 만료(최대 30일)를 기다립니다.
- OCR 글자는 노드가 없으므로 경로가 비어 있어야 합니다. 그래서 계약은 **비어 있을 수 있는 값(기본 null)**이어야 합니다.

## 5. 개인정보

- 노드 경로는 글자가 아니라 구조 정보지만, 화면 구조를 드러내므로 로그·진단에 남기지 않습니다. `ExtractedText.toString()`은 지금처럼 `redacted`를 유지합니다.

## 6. D 의견 (논의 때 제안)

1. 계약 추가는 찬성합니다. `nodePath: String? = null`(기본 null)이면 기존 호출이 깨지지 않습니다.
2. 첫 단계에서 D 지문은 새 칸을 **읽지 않습니다**. 기존 기억에 주는 영향은 0입니다.
3. 팝업 영역만 쓰는 `content.v2`는 실측에서 "뒤 화면 때문에 기억이 안 맞는 비율"을 본 뒤 정합니다(재현 앱 P13, N01/N02).
4. v2로 갈 때 필요한 시험:
   - 같은 팝업 + 뒤 화면만 다름 → v1은 다른 지문(현재), v2는 같은 지문
   - 팝업 본문이 한 글자라도 다름(N03~N06) → v1·v2 모두 **반드시** 다른 지문
   - 팝업 루트를 알 수 없음 → v2는 지문을 만들지 않거나 v1으로 대체(fail closed)
