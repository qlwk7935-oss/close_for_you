# 닫아줄게 v5 — 기능 검증 실험 계획서

> **문서 목적:** 실제 개발 **전에 지금 할 수 있는 검증**과 **앱을 개발한 후에만 가능한 검증**을 분리한다.  
> **기준:** `닫아줄게_통합설계_v5.md`의 F0~F13, G1~G5 및 Q1~Q10.  
> **상태:** 모든 실험 **미실시**. 아래의 성공 조건·권장 표본 수는 *제안된 평가 방법*이며 이미 검증된 결과나 공식 성능 기준이 아니다.  
> **기기:** 특정 모델로 한정하지 않는다. 갤럭시 Z 폴드7은 기존 TalkBack 관찰 사례이며, 개발 필수 기기가 아니다.  
> **개발 기간:** 실험 우선순위를 정하는 기준에 개발 기간 제한을 두지 않는다.

## 0. 분류 기준과 먼저 결론

| 구분 | 언제 할 수 있나? | 결과물 |
|---|---|---|
| **A. 지금 바로 — 개발 없이** | TalkBack·기존 앱·수동 화면 탐색·정답지 작성만으로 가능 | 현행 문제 실측 기록, 테스트 화면 목록, 경쟁 방식의 한계 |
| **B. 지금 바로 — 소형 실험 코드만 작성** | 완성 앱 없이 `AccessibilityService` 테스트 앱이나 독립 추론 샘플만 만들어 가능 | Android API 및 핵심 기술의 **성립 여부** |
| **C. 개발 후 — 통합 앱 검증** | 닫아줄게의 감지 → 분석 → 판단 → 실행 → 안내 흐름 구현 후 가능 | 기능 정확도, 안전성, 작업 완료율, 실사용 개선 효과 |

**핵심 원칙:** B 실험을 '개발 없이 할 수 있는 실험'으로 적지 않는다. B는 정식 제품 개발 전에 만드는 **PoC(기술 검증용 최소 코드)**다. C의 성공을 A나 B의 결과로 미리 주장하지 않는다.

### 우선순위

1. **G1 — 화면 정보 확보:** 접근성 노드가 없는/불완전한 팝업을 감지·캡처·OCR로 확인할 수 있는가?
2. **G2 — 이미지 의미 인식:** 다른 앱을 사용하는 동안 로컬 이미지 분석이 실제로 돌아가는가?
3. **G3 — 버튼 탐지·조작:** TalkBack 사용 중 라벨 없는 버튼을 찾고 안전하게 조작할 수 있는가?
4. **G4 — 음성 안내:** 화면 설명이 TalkBack 사용자에게 실제로 전달되는가?
5. **G5 — 효용 비교:** TalkBack과 기존 대체 방법보다 사용자의 과제 수행이 나아지는가?

# A. 개발 없이 지금 바로 가능한 실험

## A01. TalkBack 기본 탐색 한계 기록

- **목적:** 어떤 팝업이 TalkBack으로 읽히지 않는지 구체적인 실패 유형을 확보한다.
- **준비:** Android 폰, TalkBack, 일반 앱의 이미지 광고·공지·영상 광고·라벨 없는 버튼 사례. 민감한 실제 결제·계정 데이터는 사용하지 않는다.
- **방법:** 동일 화면을 `일반 좌우 스와이프`와, 제공된다면 TalkBack의 `이미지 설명 수동 실행`으로 각각 탐색한다. 버튼이 '버튼'으로 읽히는지, 초점에서 완전히 빠지는지, 팝업 내용의 어떤 부분이 누락되는지 나눠 기록한다.
- **기록:** 기기/Android/TalkBack 버전, 앱·버전, 화면 유형, 일반 탐색 성공 여부, 수동 설명 성공 여부, 본문 복귀 성공 여부, 소요 시간·스와이프 수.
- **성공적인 실험 결과:** `어떤 환경에서 무엇을 못 읽는가`가 재현 가능한 사례로 남음. **닫아줄게가 해결했다는 의미는 아님.**
- **실패 시:** 앱 버전·접근성 설정을 확인하고, 재현되지 않는 사례도 제거하지 말고 별도로 보관.

## A02. 기존 대안으로 같은 팝업 해결해 보기

- **목적:** TalkBack의 이미지 설명 기능, 기존 자동 스킵 앱, 광고 차단기로 어느 문제까지 해결되는지 구분한다.
- **준비:** 동일한 과제 화면, 비교할 도구의 실제 지원 앱 목록과 설정 기록.
- **방법:** (1) TalkBack 단독, (2) TalkBack + 수동 이미지 설명, (3) TalkBack + 기존 자동 스킵 앱, (4) 필요하면 네트워크 광고 차단기를 **별도** 비교한다. 광고 차단과 팝업 자동 스킵은 서로 다른 접근이므로 하나의 동일한 기능으로 취급하지 않는다.
- **기록:** 팝업 존재 여부, 내용 파악 성공, 닫기 성공, 사용자 조작 수, 사전 설정 필요 여부, 지원 불가 사유.
- **성공적인 실험 결과:** 기존 도구로 해결된 사례와 남는 문제를 분리한 비교표.
- **주의:** 기존 도구가 특정 앱을 지원하지 않으면 '도구 전체가 팝업 감지를 못 한다'고 일반화하지 않는다.

## A03. 팝업 사례 목록과 정답 기준 만들기

- **목적:** 팀이 실제 구현에서 무엇을 성공으로 볼지 먼저 정한다.
- **준비:** 테스트용 앱·화면. 가능하면 이미지 팝업, 공지, 동의, 영상, WebView, 게임·캔버스, 라벨 없는 버튼과 일반 화면 전환을 골고루 확보한다.
- **방법:** 각 화면에 `팝업 여부`, `광고/공지/사용자 결정 필요/판단 불가`, `읽어야 하는 핵심 정보`, `정답 버튼의 위치와 역할`, `안전한 동작`을 사람이 표시한다. 의견이 갈리면 분쟁 사유와 판정 기준을 기록한다.
- **기록:** 시나리오 ID, 앱, 화면 유형, 정답·판정 이유, 분류가 애매한 사례.
- **성공적인 실험 결과:** 나중에 동일 기준으로 재현 가능한 **정답지**와 사례 목록.
- **권장:** 시작 시 대표 사례 20~30개 정도부터 모을 수 있으나 표본 수는 팀이 정한다. 이것만으로 범용 성능을 주장하지 않는다.

## A04. 사용자 수요·작업 흐름 사전 조사

- **목적:** 사용자에게 필요한 것이 '무조건 자동 닫기'인지, '내용 전달 후 선택'인지 검증한다.
- **준비:** 시각장애인 협회/당사자 협조, 질문지, 개인정보·연구 동의 안내.
- **방법:** 팝업을 겪는 빈도, 많이 막히는 앱, 기존 대처법, 광고 자동 닫기 허용 범위, 공지를 읽고 닫는 방식에 대한 선호를 질문한다. 구현된 기능이 없으므로 **실사용 효과 평가라고 부르지 않는다.**
- **기록:** 사용 패턴, 가장 중요한 문제, 통제감 우려, 우선 해결 화면, 참여자별 접근성 환경(필요한 범위만).
- **성공적인 실험 결과:** 기능 우선순위와 실제 테스트 시나리오 보정에 사용 가능한 요구사항.
- **주의:** 협회에 연락했다는 사실 자체가 수요 검증 결과는 아니다.

## A05. 위험 화면 시나리오 정답지 작성

- **목적:** 안전 엔진의 테스트 기준을 코드 작성 전에 결정한다.
- **준비:** 가상 결제·개인정보 동의·구독·계정 삭제·권한·로그인·비밀번호 화면. 실 계정·실 결제 수단 금지.
- **방법:** 'X인데 실제로 광고 이동', '취소인데 구독 취소', '중요 공지에 날짜 변경'처럼 반례를 만들고, **자동 금지 / 사용자 선택 / 검증된 자동 닫기**의 기대 동작을 기록한다.
- **기록:** 위험 이유, 금지 동작, 안전한 대안, 테스트에서 확인해야 할 화면 변화.
- **성공적인 실험 결과:** F0/F7/F8/F9에 적용할 위험 테스트 목록.

# B. 완성 앱 없이 소형 실험 코드로 지금 검증할 항목

> 아래는 **바로 시작할 수 있지만 코드는 작성해야 하는** 실험이다. 가능하면 실제 개인정보가 없는 자체 테스트 앱에서 먼저 진행한 뒤 일반 앱에 적용한다.

## B01. G1 — 접근성 이벤트·노드·캡처 성립 실험

- **필요한 최소 코드:** 접근성 서비스의 창/노드 정보 출력, 이벤트 로그, 단발 캡처 버튼, ML Kit 한국어 OCR 예제.
- **방법:** 같은 화면에서 정상 대화상자, 같은 창 덮개, WebView 모달, 이미지 팝업, 캔버스 화면을 열고 `getWindows()`, `rootInActiveWindow`, 노드의 글자·클릭 가능 여부를 수집한다. 권한과 OS 조건이 충족되면 단발 캡처→OCR을 시도한다.
- **확인:** 팝업 종류별로 이벤트가 발생하는지, 접근성 정보가 비었을 때 캡처가 가능한지, 이미지 속 글자를 읽는지.
- **기록:** API 지원·권한 오류, 감지된 창/노드 수, OCR 인식 결과, 프레임 획득 실패, 지연.
- **판정:** 대상 유형에서 입력 정보 확보 가능/부분 가능/불가로 나눔. **가능했다고 해서 감지 정확도 확보로 판정하지 않음.**
- **실패 대안:** 노드 경로가 부실하면 허용된 단발 캡처 경로 검증, 캡처도 안 되면 해당 화면을 지원 제한으로 표시.

## B02. G2 — 다른 앱 전면 상태의 온디바이스 이미지 분석

- **필요한 최소 코드:** 원본 화면 캡처 전달, 앱에 포함한 로컬 모델 추론기, 모델별 처리 시간 로그. 비교용으로 자체 Activity 전면에서 ML Kit GenAI 호출 실험 가능.
- **방법:** 다른 앱을 전면에 둔 채 접근성 서비스가 **허용된 시험 화면**의 이미지를 획득하고, 앱 내 로컬 모델이 실제 문장 설명까지 생성 가능한지 시험한다. 단순 물체 라벨만 내는 모델과 구별한다.
- **확인:** 서비스 상황에서 추론 시작/종료, 백그라운드 제약, RAM·발열, 한국어 출력, 실제 팝업 핵심정보 설명 여부.
- **기록:** 모델 종류·버전·크기, 로컬/전면 실행 구분, 성공·오류 코드, 처리 시간·메모리, 사람 정답 설명 대비 누락/환각.
- **판정:** 배경 실행과 의미 설명이 각각 성공해야 이미지 의미 설명 기술이 성립했다고 판단.
- **실패 대안:** 모델 교체, 사용자가 요청해서 자체 앱 화면에서 설명, 또는 OCR/라벨만 가능한 제한 모드로 명시.
- **주의:** ML Kit GenAI의 `checkFeatureStatus()` 성공은 **다른 앱 사용 중 추론 허용**과 별개다.

## B03. G3 — TalkBack 켠 상태의 라벨 없는 버튼 실행

- **필요한 최소 코드:** 라벨 있는 버튼/라벨 없는 클릭 노드/노드 없는 가짜 X를 포함한 **자체 시험 앱**, 접근성 노드 클릭·제스처 호출 로그.
- **방법:** TalkBack 켬/끔을 나눠 E1 `ACTION_DISMISS`, E2 `ACTION_CLICK`, E3 라벨 없는 클릭 노드, E4 화면상 X 후보를 시험한다. 동작은 버튼마다 1회만 실행하고 화면 상태를 관찰한다.
- **확인:** 좌표 탭이 실제 클릭인지 포커스 이동인지, 라벨 없는 버튼의 노드가 있는지, 엉뚱한 요소를 누르지 않는지.
- **기록:** 탐지 여부, 클릭/포커스 결과, 반환값, 팝업 소멸 여부, 다른 동작 수행 여부, TalkBack 조작 충돌.
- **판정:** **버튼 발견 성공**, **기계적 클릭 성공**, **의미상 안전함**을 각각 별개로 판단.
- **실패 대안:** E4 자동화 중지, 사용자에게 위치 안내/직접 조작 제공. 실패 반환만으로 자동 좌표 재시도하지 않음.

## B04. G4 — TalkBack과 안내 오버레이 충돌

- **필요한 최소 코드:** 접근성 오버레이, pane 제목, live region, [다시 듣기]·[닫기]·[그대로] 버튼, 필요시 자체 TTS.
- **방법:** TalkBack으로 본문을 읽는 도중 안내창이 나타나게 하고, 안내가 실제 음성으로 들리는지, 버튼 탐색이 가능한지, 사용자가 원래 위치로 돌아갈 수 있는지 반복 확인한다.
- **확인:** 안내 중복/누락, 포커스 강탈, 안내 완료와 사용자 청취의 차이.
- **기록:** 음성 출력 실제 여부, 사용자 재진술 가능 여부, 포커스 변경, 재청취 성공, TTS 중복.
- **판정:** **포커스 이벤트 = 실제 들음**으로 처리하지 않는다. 사용자가 들었는지는 별도의 관찰·질문으로 확인.
- **실패 대안:** 자체 TTS와 조작 가능한 Activity 경로 검토. 그래도 안내 누락되면 자동 공지 닫기 금지.

## B05. 캡처 보호 게이트와 민감 화면 반례

- **필요한 최소 코드:** F0-A 일부(보호 앱/입력칸 감지), 캡처 허용/거부, 이미지 폐기 로그, 가짜 개인정보 화면.
- **방법:** 비밀번호·가짜 계좌 정보·일반 쿠폰 광고·이미지 형태의 가짜 결제창을 차례로 표시해 캡처가 발생하는지 본다. 정상 광고까지 과도하게 차단하는지도 확인한다.
- **기록:** 차단/허용, 캡처 발생, 폐기, 로그에 원문 잔존 여부, 오차단 사례.
- **판정:** 보호 대상에서 금지된 캡처·전송이 발생하면 실패. **완벽한 민감 화면 감지라고 주장하지 않음.**
- **실패 대안:** 차단할 앱·화면 범위 확대, 기능을 사용자가 허용한 앱으로 제한.

## B06. 영상 프레임·오디오 제약 사전 확인

- **필요한 최소 코드:** 일정 간격 단발 캡처 및 프레임 변화 검출; 오디오를 실험한다면 별도 사용자 동의와 시험 앱.
- **방법:** 재생 UI/자막/카운트다운이 접근성 트리 또는 캡처에 나타나는지 확인. 프레임 간 중요한 장면이 누락되는지 검사한다. 오디오 캡처는 허용한 앱에서만 시험한다.
- **기록:** 프레임 획득 성공, 텍스트/버튼 검출, 시간순 장면 누락, 오디오 캡처 허용 여부.
- **판정:** 영상 내용 전체를 이해한 것이 아니라 **일부 프레임/음성 정보 추출 가능성**을 확인하는 실험.

# C. 닫아줄게 구현 후 검증해야 하는 실험

> 이 단계에서는 반드시 **완성된 기능들이 연결된 결과**를 평가한다. PoC에서 API가 작동했다는 사실은 C의 합격을 대신할 수 없다.

## C01. 전체 팝업 감지 성능 (F1·G1)

- **절차:** 라벨 있는 대화상자, 같은 창 덮개, 작은 팝업, WebView, 이미지 전면 광고, 캔버스, 키보드·토스트·일반 페이지 전환을 동일한 정답 기준으로 시험한다.
- **측정:** 팝업 감지 정밀도·재현율, 유형별 미탐 건수, 오탐 건수, 감지 지연.
- **필수 구분:** '팝업을 발견함'과 '광고라고 분류함'은 다른 결과로 기록.
- **실패 조건:** 일반 화면 전환을 자동 클릭 대상으로 처리하거나 중요한 팝업을 지속해서 놓치면 설계 재검토.

## C02. 이미지 글자·그림 의미 설명 (F2·F4·G2)

- **절차:** 문자 중심 이미지, 글자가 없는 포스터, 버튼 아이콘, 공지 이미지, 상품 홍보 이미지에서 OCR과 비전 모델의 결과를 분리 측정한다.
- **측정:** OCR 문자 오류율(CER), 날짜/금액/핵심사항 정확도, 이미지 설명 핵심 대상 일치, 환각·누락, 모델 미지원 비율, 지연.
- **실패 조건:** 단순 물체 라벨링 결과를 '공지의 의미를 이해했다'고 판정하면 안 됨.

## C03. 라벨 없는 버튼과 실제 안전 클릭 (F3·F8·F9·G3)

- **절차:** E1~E4, 화면 회전·화면 크기 변경, 가짜 X, 클릭은 되지만 외부 이동을 일으키는 버튼을 시험한다.
- **측정:** 버튼 탐지율, 기능 판별 정확도, 닫기 완료율, 오클릭/부작용, TalkBack 제스처 충돌.
- **필수 구분:** `팝업이 사라짐`은 기계적 성공이지 `원하는 안전한 동작`을 보증하지 않음.
- **실패 조건:** 중요한 동작을 잘못 실행하면 해당 자동화 경로 중단·수정.

## C04. 팝업 4분류 성능 (F7·F8)

- **절차:** 광고, 공지, 사용자 결정 필요, 판단 불가의 별도 정답 세트로 시험한다. 새로운 앱의 화면은 개발용과 분리한다.
- **측정:** 혼동행렬, 각 분류 정밀도·재현율, '사용자 결정 필요 → 광고' 오분류, 판단 불가 비율.
- **실패 조건:** 위험 화면을 자동 허용 대상으로 이동시키는 오류 발생 시 우선 해결.

## C05. 공지 처리와 내용 변경 (F10·F12)

- **절차:** 최초 공지, 동일 공지 반복, 날짜만 변경, 시간만 변경, 금액 변경, 행동 요구 문구 추가, 본문 완전 변경을 순서대로 표시한다.
- **측정:** 내용 전달 정확도, 재청취 성공, 이전 허락의 잘못된 재사용, 내용이 바뀐 공지의 자동 닫기 수.
- **실패 조건:** 바뀐 공지가 이전 기억으로 자동 닫히면 실패.

## C06. 위험 동작·민감정보 보호 (F0·F8·F9)

- **절차:** 가짜 결제·로그인·권한·삭제·동의·보안 키패드 화면에서 자동 실행과 캡처·저장·전송 규칙을 확인한다.
- **측정:** 금지 행동 실행 건수, 민감 화면 캡처/저장/업로드 건수, 정상 팝업의 잘못된 차단 비율.
- **합격 방향:** 계획된 시험 범위에서 금지 행동·유출 0건 목표. **0건 관측은 영구적으로 안전하다는 증거가 아님.**

## C07. 영상 광고와 영상 내용 설명 (F5·F6)

- **절차:** 광고 표지가 있는 영상/없는 영상, 건너뛰기 버튼/없는 영상, 자막 있는/없는 영상, 소리 캡처 가능/차단 사례를 구분한다.
- **측정:** 영상 탐지와 광고 분류 각각의 정밀도·재현율, 스킵 성공률, 잘못된 스킵, 장면 순서, 자막 인식, 환각·정보 누락, 지연/발열.
- **실패 조건:** 일부 프레임만 보고 영상 전체의 의미를 정확히 이해했다고 주장하면 안 됨.

## C08. 연속 팝업·상태 관리 (F11)

- **절차:** 광고→공지→권한창, 같은 창 재등장, 다중 이벤트, 버튼 실행 도중 사용자 터치, TalkBack 빠른 탐색, 앱 전환을 시뮬레이션한다.
- **측정:** 중복 클릭, 미탐 팝업, 실행 직전 무효화 성공률, 사용자 조작과 충돌 건수, 연쇄 차단 작동.
- **실패 조건:** 사용자가 조작하는 동안 자동화가 끼어들거나 위험창까지 연쇄 클릭하면 실패.

## C09. 사용자 선택 기억·바인딩 (F12)

- **절차:** 사용자가 확인한 동일 광고 반복, 버튼 위치·아이콘 변경, 앱 업데이트, 팝업 내용 변경, 이전 허락 취소를 시험한다.
- **측정:** 재확인 횟수 감소, 기억의 정확한 재사용, 부적절한 자동 재사용, 설정 삭제 후 완전 해제 여부.
- **실패 조건:** 안전성이 바뀐 화면에 오래된 바인딩을 적용하면 실패.

## C10. TalkBack 안내·음성 명령 (F10·F13·G4)

- **절차:** 사용자가 본문을 읽는 중 알림, 다시 듣기, 닫기, 그대로 두기, 영상 설명 요청, 소음 환경에서 음성 명령, 자체 TTS 대체 경로 시험.
- **측정:** 사용자가 이해한 정보, 안내 누락·중복, 포커스 손실, 명령 정확도·오인식 시 실제 오동작, 재청취 성공.
- **실패 조건:** TalkBack 포커스 이벤트만으로 정보 전달 성공이라고 판정하면 안 됨.

## C11. 기기·Android 버전 호환성

- **절차:** 가능하면 제조사·Android 버전·화면 크기가 다른 기기에서 동일한 대표 실험을 반복한다. 특수 기종 하나로 전체 Android 지원을 주장하지 않는다.
- **측정:** 기능 지원 여부, 화면 캡처 경로(API 30/34 차이), 모델 추론/메모리, TalkBack 안내, 제스처 차이, 실패율.
- **실패 조건:** 미지원 기기에서 기능 지원으로 잘못 표시하거나 안전하게 중단하지 못함.

## C12. 실제 시각장애인 당사자 사용성 비교 (G5)

- **절차:** **A=TalkBack 단독**, **B=TalkBack+기존 자동 스킵 도구**, **C=TalkBack+닫아줄게**를 같은 과제로 비교한다. 네트워크 광고 차단기는 동작 방식이 다르므로 필요 시 별도 비교. 조건 순서를 바꾸어 연습효과를 줄인다.
- **과제 예:** 이미지 공지의 점검 날짜 알아내기, 라벨 없는 광고 닫고 본문 첫 정보 찾기, 중요 결제창을 건드리지 않고 정보 확인하기, 영상에서 스킵 버튼 찾아 나가기.
- **측정:** 과제 완료율, 완료 시간, 스와이프 횟수, 정보 이해 정확도, 오작동, SUS/신뢰·통제감 인터뷰.
- **참가:** 협회 협조를 받아 실제 TalkBack 사용자를 섭외하는 것이 목표. 팀원들이 화면을 가리고 수행하는 실험은 사전 연습이지 당사자 검증이 아님.
- **윤리·안전:** 참여 동의·중단권·시험용 가짜 데이터. 실제 금융·개인 메시지·계정 접근 요구 금지.
- **실패 조건:** 닫는 속도만 빨라지고 중요한 정보를 더 많이 놓치거나 불안을 높이면 개선이라고 판정하지 않음.

## C13. 자동화 적용 범위 및 실패 원인 종합

- **절차:** 전체 팝업을 `자동 처리 / 사용자 확인 후 처리 / 안내만 / 감지 실패 / 의도적으로 차단`으로 집계하고, 분모를 전체 팝업·지원 팝업으로 나눠 공개한다.
- **측정:** 자동 처리 커버리지, 사람의 조작 부담, 위험 조작률, 미지원·오탐·모델 불가·보호 중단이 차지하는 비율.
- **실패 조건:** 모든 화면을 차단해서 위험 클릭 0건만 달성한 것을 성공으로 평가하지 않음.

## C14. 배포 가능성 점검 (기능 성능과 별도)

- **절차:** 배포 목표가 생기면 Google Play의 접근성 서비스·다른 앱 광고 표시 방해 정책과 데이터 안전 고지 등을 별도 검토한다.
- **기록:** 기능 목적, 사용자 옵트인, 정책 문구, 배포 방식, 미해결 쟁점.
- **주의:** 사용자 동의가 있다고 Play 승인되는 것이 아님. 수업 시연 가능 여부와 공식 배포 승인 가능성도 별개다.

# F. 지금 바로 실행할 순서

1. **A01·A02:** 실제 TalkBack 탐색과 기존 도구 비교 영상을 남기고, 실패 화면을 유형별로 나눈다.
2. **A03·A05:** 이미지·영상·위험 팝업 정답지와 안전 금지 목록을 만든다.
3. **B01:** 최소 접근성 서비스로 노드·창·캡처·OCR 가능 여부를 실기기에서 확인한다.
4. **B03:** 최소 가짜 팝업 앱으로 TalkBack과 노드 클릭/좌표 제스처 충돌을 확인한다.
5. **B02:** 다른 앱을 전면에 둔 상태에서 실제 로컬 이미지 설명 모델을 돌려본다.
6. **B04:** 팝업 음성 안내와 다시 듣기를 사용자에게 전달할 수 있는지 확인한다.
7. **그 후:** C01~C13의 통합 테스트를 설계·시행하고 협회 당사자 테스트(C12)를 진행한다.
